### 0.2 一句话根因（解释 R1 为什么 BLOCKED）

现有逐帧 PNG 是 `sc_decode.py` 的产物：它按 **`.sc` 内的 shape 定义顺序**逐个渲染（`for x in range(ShapeCount)`），
把每个 shape 的若干 region 从图集 `_tex.png` 裁下、**合成到一张统一尺寸的画布**上，输出
`<name>_sprite_<shape序号>.png`；而同一份 `.sc` 里的 **Animation 块（tag `0c`）被解析后直接丢弃、不产出任何文件**。
⇒ 逐帧 PNG 保留了**像素**，丢掉了**分组**；序号是"美术对象序号"，既不是时间序，也不是图集 texel 序。
（R1 观察到"相邻帧距离中位 112~128、无互不相似的 4 段"完全符合"shape 定义序 + 相邻 shape 常属同一动作族"。）

## 2. 路径 B：`*_tex.png` 与逐帧 PNG 到底是什么关系（**本片核心证据**）

### 2.1 做了什么 / 拿到什么（尺寸与像素统计）

用 PIL 实测（脚本 `.ai-tmp/test/A1-atlas-vs-frames.py`，输出见下）：

| 单位 | 图集 `*_tex.png` 尺寸 | 逐帧 PNG 尺寸（**全部同尺寸**） | 帧数 | 图集不透明像素 | 逐帧不透明像素**总和** | 比值 |
|---|---|---|---|---|---|---|
| chr_knight | **1276 × 2028** | **187 × 181**（486/486 帧一致） | 486 | 1,168,505 | 1,987,551 | **1.70×** |
| chr_archer | **892 × 2022** | **130 × 135**（252/252 一致） | 252 | 722,855 | 1,074,264 | **1.49×** |
| chr_musketeer | **1022 × 1340** | **120 × 142**（414/414 一致） | 414 | 717,627 | 1,383,460 | **1.93×** |

另：knight 逐帧**内容包围盒**（去掉透明边）w: min 50 / 中位 84 / max 133，h: min 71 / 中位 103 / max 144
（⇒ 每帧画布 187×181 里，内容只占约 84×103，**大量透明边**）。

**两条硬事实**：
1. **逐帧 PNG 的尺寸在整个目录内完全一致**（187×181 / 130×135 / 120×142）—— 这不是"按内容紧裁剪"的切块，
   而是**统一画布**。
2. **逐帧不透明像素总和 = 图集的 1.5~1.9 倍** —— 若逐帧是图集的**互斥切块**，这个比值**必须 ≤ 1**。
   ⇒ **逐帧 PNG 不是图集 texel 的切块。**

### 2.2 图集长什么样（看图，`.ai-tmp/screenshots/A1-atlas-chr_knight.png`）

- 图集是**随机紧密 bin-packing**（不是规则网格）：大量骑士小图（约 40~55 px 高）+ 底部约 22% 是成片的
  **红色弧形件**（`A10-atlas-knight-bottom.png`；疑为红队/刀光类 shape 族）。
- **不存在"每行每列一个帧"的网格** ⇒ 即使按 texel 顺序编号，也**没有**一个自然的"行主序"帧序可言。

### 2.3 决定性出处：产出这些 PNG 的工具源码

R1 的怀疑（"顺序 = 图集 texel 顺序"）**可以被工具源码直接否证**。

**工具链**（`smlbiobot/cr` 主仓库 README 逐条写明）：

> 出处：`https://raw.githubusercontent.com/smlbiobot/cr/master/README.md` 第 16-25、42-52 行：
> - "CR-SC-Dump is used to decrypt sc/*_tex.sc files which output image sprites of the character animations
>    — Source: https://github.com/123456abcdef/cr-sc-dump"
> - "Additionally, sc_decode is used to turn the sprites into useful frames.
>    — Source: https://github.com/umop-aplsdn/sc_decode ；High-Res / Low-Res capable Fork: https://github.com/Galaxy1036/sc_decode"
> - 步骤 6："Run `find . -not -name '*.png' -not -name '*.py' -exec python3 ./sc_decode.py -s {} \;` in ./assets/sc folder"
> - 步骤 2 产出 `*_tex.png`（`dumpsc.py` 解密 `*_tex.sc`）；步骤 6 产出各 `<name>_out/` 目录。

**源码（`Galaxy1036/sc_decode`，已拉到本地 `.ai-tmp/test/scdfull/sc_decode.py`，15218 字节）关键行**：

| 行为 | 出处 `文件:行` |
|---|---|
| 读 `.sc` 头部：`ShapeCount / TotalsAnimations / TotalsTexture / … / ExportCount` | `sc_decode.py:252-272` |
| **`12` 块 = Polygon（一个 shape：n 个 region，各带 shape 顶点 + 图集 UV）** | `sc_decode.py:310-355` |
| **`0c` 块 = Animation：读 `ClipID / ClipFPS / ClipFrameCount / … shapeID 列表 / 名称串`，然后 `continue`（丢弃）** | `sc_decode.py:364-393` |
| 图集来源：`Image.open(filein + '_tex' + … + '.png')` | `sc_decode.py:92`、`265-266` |
| 每条 shape 从图集按多边形裁下（`sheetimage[sheetID].crop(bbox)`） | `sc_decode.py:105-124` |
| **合成到"全 shape 统一画布"**（画布尺寸 = 所有 shape 的 maxLeft/maxRight/maxAbove/maxBelow，再 +2） | `sc_decode.py:10-79`、`103` |
| 输出目录与文件名：`pathout = <filein> + '_out'`；`save(pathout + '/' + filein + '_sprite_' + str(x).rjust(maxrange,'0') + '.png')` | `sc_decode.py:138`、`143-147` |
| 主循环：`for x in range(ShapeCount)` ⇒ **序号 = shape 定义序** | `sc_decode.py:18`、`95` |

**结论（路径 B）**：
1. **`frame_NNN` 的顺序 = `.sc` 里 shape 的定义顺序**（`ShapeCount` 从 0 起）；
   **既不是**动画时间序，**也不是**图集 texel 顺序（图集本身是随机打包，无行主序可言）。
2. 逐帧 PNG 尺寸全一致，是因为工具**把每个 shape 画到统一画布**（这也顺带解释了客户端已实测的
   "486 帧里 245 个不同锚点、并集正好是整幅画布"，见 `client/Assets/Scripts/View/UnitView.cs:413-425`）。
3. **动画索引确实存在，但在 `.sc` 的 `0c` Animation 块里，且 `sc_decode` 把它丢掉了。**
   ⇒ 现有 PNG **在信息论上不可能**还原 idle/walk/attack/die 分组 —— R1 的 BLOCKED 是**必然**。

### 2.4 直接否证 R1 的图集顺序假设（统计）

| 假设 | 可检验推论 | 实测 | 判定 |
|---|---|---|---|
| 逐帧 = 图集互斥切块（texel 序） | `Σ(逐帧不透明像素) ≤ 图集不透明像素` | 1.49~1.93× **> 1** | **否证** |
| 逐帧 = 图集切块 | 逐帧尺寸随内容变化 | 每目录**恒定**（统一画布） | **否证** |
| 图集可给出"行主序"帧序 | 图集是规则网格 | 随机 bin-packing（看图） | **否证** |
| `frame_NNN` = shape 定义序 | 源码 | `sc_decode.py:95,138` | **成立** |

> 说明：本片**没有**得出"顺序 = 图集 texel 顺序"，因此不需要"逐帧↔图集 texel 对应关系统计"；
> 反向证据（上表三条 + 工具源码）已足够。曾尝试 FFT-NCC 逐帧回贴图集（`.ai-tmp/test/A5-ncc.py`），
> 因图集内大量近似重复的 shape（互相干扰、argmax 不稳）**未作为判据采用**，仅记录为"方法试过但退化"。

### 4.2 `.sc` 与 `cr-assets-png` 的关系（这是**唯一必须知道**的一句）

- APK 里单位是**两个文件**：`<name>.sc`（**动画/形状/导出名**）+ `<name>_tex.sc`（**图集**）。
- `cr-assets-png` 里的 `chr_knight_tex.png` = 解密 `<name>_tex.sc` 的产物；
  `chr_knight_out/*.png` = 解析 `<name>.sc` 后按 shape 渲染的产物（§2.3）。
- ⇒ **`cr-assets-png` = "APK 的 `.sc` 被工具跑过一遍之后的、只剩像素的下游产物"**。
  **索引在 `.sc` 里，被这一步丢了。**

### 4.3 结论

- APK 可得性：**页面可得，但本环境抓不动**；**且不必抓** —— `.sc` 原始文件 GitHub 已有镜像（§3.4），
  比 APK（几十~上百 MB）小几个数量级。
- 若将来确实需要现代 APK（例如要 `.sc` 的 SC2 版 + `.sctx` 贴图），**需用户在浏览器里人工下载**
  （本环境被 Cloudflare 挡），或换一台能过 bot 校验的机器。

## 5. 对客户端的影响（结论写清）

### 5.1 `UnitView.AnimRanges` **该不该填？**

**⛔ 不该填（现在）。** 理由：

- `AnimRanges` 的语义是"`spriteDir → 4 档 (start,count)`"（`client/Assets/Scripts/View/UnitView.cs:57-63`）。
  当前**没有任何一处**能给出这个 `(start,count)` 的**出处**——本地素材（§1）、
  shape 序号（§2.3）、联网公开索引（§3）**都没有** frame→动作 的分段。
- 填 = **编造**，违反全局 skill 铁律 3（"写不出出处的量不许进工程"）与本项目硬规则 9。
- 现有代码的**设计已经是对的**：`AnimRanges` 恒空时，`ClipStart()` 返回 0、`ClipEnd()` 返回整目录长度
  （`UnitView.cs:302-317`），即"整目录循环"。**这是当前唯一有出处的行为**。

### 5.2 "整目录循环"要不要保留？

**保留（作为已登记差异）。** 理由：

- 它是"素材缺索引"下的**最保守**行为，且**已登记**在 `UnitView.cs:20-34` 的类注释与
  `策划/验收表.md` 的「允许的差异」（列：差异 / 为什么 / 出处 / 何时消除）。
- **消除条件不变**：拿到帧段清单后**只填 `AnimRanges`、逻辑不动**（`UnitView.cs:32-33` 已是此设计）。

### 5.3 如果将来要真正消除差异，怎么走（代价）

| 步骤 | 具体动作 | 代价 |
|---|---|---|
| 1 | 取**与现有 PNG 同版本**的 `.sc`：现有素材是 `cr-assets-png` tag `2.1.5`（2018）；`smlbiobot/cr` 里的是 `1.0.0` iOS 版 —— **shape 序号可能对不上**，需先核对（比对 `ShapeCount` 是否 = 486） | 低（下几个 KB~MB） |
